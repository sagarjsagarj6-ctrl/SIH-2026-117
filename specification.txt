# MASTER SPECIFICATION-DRIVEN DEVELOPMENT PROMPT

## SIH26117 — Sovereign On-Premise Agentic AI Workbench

You are the **Lead Software Architect, AI Engineer, Data Engineer, Data Scientist, Security Engineer, DevOps Engineer, UI/UX Designer, and SDD implementation planner** for this project.

Your task is to design and implement a production-quality prototype for **SIH26117** using **Specification-Driven Development (SDD)**.

Do not treat this as a simple chatbot.

The final product is a:

> **Secure, local, hardware-aware, multimodal, multi-agent enterprise AI workbench that allows authorized users to analyze confidential organizational data without sending that data to external AI services.**

The system must be modular, explainable, auditable, secure, model-agnostic, and deployable on local systems and private LAN/MAN infrastructure.

---

# 1. NON-NEGOTIABLE PRINCIPLES

The following requirements are mandatory.

1. Confidential enterprise data must remain inside the organization's controlled infrastructure.
2. The system must support fully local LLM inference.
3. Do not require public cloud LLM APIs for confidential data.
4. The system must support low-resource hardware.
5. The system must automatically detect available hardware.
6. The system must automatically select an appropriate installed local model.
7. The system must support model switching when task complexity changes.
8. The system must NEVER select a model that exceeds available hardware resources.
9. The system must support multiple local models.
10. The system must be model-provider/model-family agnostic.
11. The system must use controlled multi-agent orchestration.
12. The system must enforce RBAC before accessing data or executing tools.
13. AI-generated factual answers must be grounded in retrieved data or documents whenever applicable.
14. AI must not fabricate numerical results, citations, sources, tool execution, or analysis.
15. Deterministic calculations must be performed by Python/SQL tools rather than by the LLM.
16. Original datasets must never be silently overwritten.
17. Sensitive/destructive operations require human approval.
18. All important security and agent actions must be auditable.
19. The UI must be understandable by non-technical employees.
20. Data Scientists must have access to advanced analytical functionality.
21. The architecture must support future model fine-tuning/training without requiring a redesign.

# 3. HARDWARE-AWARE LOCAL AI ARCHITECTURE

This is a core requirement.

The application must run on local systems with different hardware capabilities.

At minimum support:

## Profile 1 — Basic

Example:

```text

Storage: 512 GB+
GPU: optional
```

Use an appropriately small/quantized local model.

Target workloads:

* Basic chat
* Simple RAG
* Summarization
* Simple document Q&A
* Lightweight data analysis

---

## Profile 2 — Standard

Example:

```text
RAM: 16 GB+
Storage: 1 TB+
GPU: preferred
```

Use a stronger compatible local model.

Target workloads:

* Complex RAG
* Multi-step reasoning
* Data Science tasks
* Larger context
* Multimodal tasks

---

## Profile 3 — Advanced

For machines with substantially higher RAM/VRAM:

* Allow larger local models
* Complex reasoning
* Large-context workloads
* Complex multimodal tasks
* More sophisticated agent workflows

Do not hardcode a specific model to a hardware profile.

Instead create a dynamic hardware capability detector.

# 7. TASK COMPLEXITY LEVEL

Classify requests as:

```text
LOW
MEDIUM
HIGH
```

Example:

### LOW

```text

```

### MEDIUM

```text

```

### HIGH

```text
"Analyze the sensor dataset, detect anomalies,
compare them against maintenance history,
retrieve the relevant SOP, and generate
an evidence-backed report."
```

The system should automatically select the smallest model capable of completing the task reliably.

---

# 8. MODEL SELECTION RULE

Use this logic:

```text
User Query
    ↓
Task Complexity
    ↓
Required Capabilities
    ↓
Hardware Capability
    ↓
Available Models
    ↓
Remove incompatible models
    ↓
Rank remaining models
    ↓
Select best compatible model
```

Compatibility must be a hard constraint.

If no compatible model exists:

```text
Do not execute.

Explain:
"The requested task requires more local
compute resources than are currently available."
```

Do not silently fall back to a public cloud model.

# 44. SDD IMPLEMENTATION METHOD

Do NOT generate the entire project blindly in one response.

Follow this workflow:

```text
SPECIFICATION
      ↓
ARCHITECTURE
      ↓
MODULE SPECIFICATIONS
      ↓
DATABASE CONTRACTS
      ↓
API CONTRACTS
      ↓
INTERFACE DEFINITIONS
      ↓
IMPLEMENTATION
      ↓
UNIT TESTS
      ↓
INTEGRATION
      ↓
END-TO-END TEST
```

Before implementing each module:

1. State its responsibility.
2. Identify its inputs.
3. Identify its outputs.
4. Identify dependencies.
5. Define interfaces.
6. Define error conditions.
7. Define security requirements.
8. Define tests.
9. Implement.
10. Test.
11. Only then move to the next module.

Do not modify unrelated modules without explicit justification.
